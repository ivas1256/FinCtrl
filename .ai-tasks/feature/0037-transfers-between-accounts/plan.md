## Ручная проверка
- Миграция: повторный запуск без ошибок; INSERT дубля в транзакции падает на `UQ_Payments_Account_Date_Sum` (ROLLBACK).
- `TransferRepository` и join в `SelectPayment` — запросы на dev-базе.
- Preview: «Счета» — флажок сохраняется после перезагрузки; главная и «Операции» без ошибок, в ответе API есть `transferId`/`transferPairPaymentId`.

## Риски и открытые вопросы
- Если в базе уже есть дубли «счёт + дата + сумма», индекс не создастся — нужно решение пользователя.

## Журнал решений
- 2026-11-06: работа поэтапно в одной ветке, план каждого этапа согласуется; коммит — только по просьбе пользователя.
- 2026-11-06: повтор строки в файле тихо схлопывается `FindDuplicate`, ошибки нет.
- 2026-11-06: `Transfers.InPaymentId` — фильтрованный уникальный индекс (`WHERE InPaymentId IS NOT NULL`).
- 2026-11-06: фильтрованные индексы требуют `QUOTED_IDENTIFIER ON` для любого DML по `Payments`/`Transfers`; `sqlcmd` по умолчанию его выключает — в CLAUDE.md команда накатки миграций дополнена флагом `-I`. SqlClient включает опцию сам.
- 2026-11-06: этап 1 проверен: дублей «счёт + дата + сумма» в dev-базе нет; миграция накатана дважды без ошибок; дубль по счёту отклоняется индексом, две строки без счёта проходят (INSERT в транзакции с ROLLBACK); временная строка в `Transfers` (удалена после проверки) дала в `GET api/PaymentsApi/list` `transferId` и `transferPairPaymentId` второй стороны; «Счета» — флажок сохраняется и переживает перезагрузку, возвращён в исходное значение.
- 2026-11-06: этап 2 — при строке со счётом дубль ищется на том же счёте, затем среди платежей без счёта (им дозаполняется счёт). Только точный ключ «счёт + дата + сумма» продублировал бы при повторной загрузке тысячи старых платежей без счёта. Совпадение на том же счёте проверяется первым, поэтому дозаполнение не нарушает `UQ_Payments_Account_Date_Sum`. Выбор вынесен из SQL в `PaymentService` ради юнит-тестов.
- 2026-11-06: `PaymentType` найденного дубля импорт не меняет и раньше: `Update` пишет тип, прочитанный из БД. Сумма сравнивается как хранится — импорт пишет её как в файле, `NormalizeSumSign` работает только при чтении.
- 2026-11-06: этап 2 проверен: запрос `GetByDateAndSum` на dev-базе возвращает всех кандидатов по возрастанию id; end-to-end загрузка файла не выполнялась, чтобы не менять данные dev-базы, — сценарии покрыты юнит-тестами.
- 2026-11-06: этап 3 — представление переводов: связанная пара — строка `(Out, In)`; списание без второй стороны — строка `(Out, NULL)`; поступление без второй стороны строки не имеет (`OutPaymentId` обязателен), оно перевод только по типу.
- 2026-11-06: этап 3 — снятие отметки или отвязка с одной стороны оставляет вторую сторону переводом без пары (сама в траты/доходы не возвращается).
- 2026-11-06: этап 3 — «уже в переводе» (409 и исключение из кандидатов) — только платёж, связанный со второй стороной; перевод без пары можно связать.
- 2026-11-06: этап 3 — кандидаты без счёта подходят (исключается только тот же счёт): в dev-базе счёт есть у малой части операций. В PUT «другой счёт» не проверяется — только условия постановки.
- 2026-11-06: этап 3 — коммит этапа не делается по просьбе пользователя.
- 2026-11-06: этап 3 — ручная проверка нашла баг: расход, сохранённый с положительной суммой (legacy, 1 532 шт. в dev-базе), после смены типа на `Transfer` читался поступлением — `NormalizeSumSign` работает только для `Spending`. Кандидатов не было, «тот же знак» давал 409 вместо 400, снятие отметки сделало бы его доходом. Исправление: `PaymentRepository.Update` пишет нормализованную сумму (все вызывающие передают платёж, прочитанный из БД). Чтобы повторный импорт файла с положительным «Списанием» не создал дубль такого платежа, `FindDuplicate` получил тип строки и для расхода с положительной суммой ищет обе суммы (`GetByDateAndSums`). Риск: если у того же счёта и даты уже есть строка с нормализованной суммой, `Update` упадёт на `UQ_Payments_Account_Date_Sum` (500) — на dev-базе таких нет.
- 2026-11-06: этап 4 — строка отчёта платежа считается один раз и для группировки, и для «ВСЕГО»: раньше «ВСЕГО» брало итоговую категорию, и перевод со старой категорией «Еда» попал бы в итог трат. Шкалу тепловой карты не меняли — «Переводы» входят в неё, как «Накопления».
- 2026-11-06: этап 4 проверен в preview на dev-базе (7403 → 7540, июнь 2026): «Квартира» −15 984 → −5 984, «Переводы» −10 000, «ВСЕГО» −197 901,02 → −187 901,02, «Накопления» без изменений (7540 с категорией «Накопления» остался там); строка приглушена, Δ серая «новые переводы»; клик по ячейке «Переводы» показывает 7403 (красная сумма), модалка — с отметкой и парой 7540; дашборд, июнь: 194 061,02 с переводом против 204 061,02 без. Ошибок в логах backend нет. Данные возвращены в исходное состояние.
- 2026-11-06: этап 3 проверен в preview на dev-базе (пара 7403 → 7530, счёт 1 временно накопительный): кандидаты 7540/7417/7530 по близости даты, знак 7403 (хранился +10 000) нормализован; галочка → select; выбор 7530 → «Накопления», снятие галочки → «Квартира»; сохранение → строка `(7403, 7530)`, обе стороны тип 2; 409 «уже связана» для 7085→7530, 400 «тот же знак» для 7085→7403, 400 «сам платёж», 400 «не перевод»; повторное открытие — галочка и выбранная 7530; «Не указывать» → `(7403, NULL)`, 7530 остаётся переводом; снятие галочки → 7403 тип 1, строка удалена. Ошибок в логах backend нет. Данные dev-базы возвращены в исходное состояние (типы, категории, сумма, `LastUpdatedAt`, `IsSavings`).

## Вне объёма (найдено попутно)
- Этап 3: в БД есть расходы с положительной суммой (импорт пишет сумму как в файле, `NormalizeSumSign` — при чтении) — знак для подбора кандидатов в переводы и валидации брать у нормализованного платежа, не из SQL.

## Итог
Сделаны все 4 этапа: схема (`Transfers`, `Accounts.IsSavings`, `UQ_Payments_Account_Date_Sum`), импорт по ключу «счёт + дата + сумма», отметка перевода и связь сторон в модалке главной с автоподстановкой «Накоплений», строка «Переводы» вне «ВСЕГО» и исключение переводов из трат дашборда. Попутно: `PaymentRepository.Update` пишет нормализованную сумму, цвет суммы в `PaymentList` — по знаку.
