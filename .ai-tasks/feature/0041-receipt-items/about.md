# [0041] Таблица позиций чеков, привязанных к платежам

- **Ветка:** `feature/0041-receipt-items`
- **Репозитории:** backend `FinCtrl/` (миграция БД + API чтения чека, `hasReceipt`), frontend `FinCtrl.Frontend/` (просмотр чека на главной)
- **Создана:** 2026-11-10

## Контекст
Банк отдаёт только сумму операции, а электронный чек ОФД (письмо .eml, например «Пятёрочка» на 1365.89 ₽) содержит
состав покупки. Чтобы потом раскладывать траты по товарам, нужно место для позиций чека, связанное с платежом.

## Постановка
Спроектировать и накатить на dev-базу отдельную таблицу позиций чека, связанную с `Payments`. Поля — строго как в чеке:
название позиции, цена, количество с единицей измерения (кг, шт., г и т.д.), итоговая цена; плюс `CreatedAt` и
время обновления.

Решения (приняты самостоятельно):
- Одна таблица `ReceiptItems` (строка — позиция) с `PaymentId` FK; отдельной таблицы-заголовка чека нет — его поля
  (продавец, ИНН, ФН/ФД/ФПД) в постановку не входят.
- Количество — `DECIMAL(18,3)` (весовой товар 0.624 кг).
- Единица измерения — справочник `Units` (по запросу пользователя): `UnitName NVARCHAR(20)` уникальное, как
  напечатано в чеке («кг», «шт.»); в позиции — `UnitId` FK. Миграция заполняет справочник частыми единицами
  (шт., кг, г, л, мл); остальные будет создавать импорт по паттерну get-or-create по названию.
- Цена и итог — `DECIMAL(18,2)`, как `Payments.PaymentSum`.
- Время обновления называется `LastUpdatedAt` (NULL) — как во всех таблицах проекта; `CreatedAt` — `DATETIME2 NOT NULL`.
- Без каскадного удаления, как у `PaymentTags`/`Transfers`: платежи удаляются мягко.

Дополнение (запрос пользователя): backend-API получения чека по платежу —
`GET api/PaymentsApi/{paymentId}/receipt` (контракт — в `plan.md`). Решения (приняты самостоятельно):
- платёж без позиций — 200 с пустым `items` и `totalSum = 0` («нет чека» — не ошибка);
- несуществующий или удалённый платёж — 404;
- работа ведётся в той же ветке без коммитов (по запросу пользователя).

Дополнение 2 (запрос пользователя): просмотр чека в UI. Из трёх макетов (таблица / бумажный чек / сводка с долями)
пользователь выбрал **«бумажный чек»**; кнопка — на главной странице в списке платежей ячейки (`PaymentList`).
Решения (приняты самостоятельно):
- кнопка 🧾 «Открыть чек» — у каждого платежа рядом с ✏️ (признака чека в списке нет, узнать можно только запросом);
- модалка узкая (`modal-dialog` по умолчанию), моноширинный шрифт: шапка «Кассовый чек · #id» + дата операции;
  позиция — две строки: название, затем «количество единица × цена ……… итог»; внизу пунктир и «ИТОГ»;
- загрузка — спиннер; пустой чек — «У этой операции нет чека»; ошибка — `detail` через `useAlerts`;
- если `totalSum` ≠ модуля суммы операции — приглушённая строка «Сумма операции: …» (не ошибка);
- только просмотр, кнопок правки нет; повторное открытие перезапрашивает чек.

Дополнение 3 (запрос пользователя): признак наличия чека приходит с backend, кнопка без чека неактивна.
Решения (приняты самостоятельно):
- новое поле платежа `hasReceipt: bool` (= есть хотя бы одна строка `ReceiptItems`) во всех ответах с платежами
  (через `SelectPayment` → `PaymentDto` Infrastructure → `PaymentDto` Website), только чтение, в `EditPaymentRequest` не входит;
- кнопка 🧾 у платежа без чека — `disabled` с подсказкой «Чека нет»; модалка остаётся (текст «нет чека» — на случай гонки).

## Вне объёма
- Запись/правка позиций через API и UI; кнопка чека на странице «Операции».
- Разбор писем с чеками и импорт позиций.
- Заголовок чека и фискальные реквизиты, НДС позиции.
