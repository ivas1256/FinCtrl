# Регламент работы над задачей

Обязателен для любой задачи, которая меняет код в `FinCtrl/` или `FinCtrl.Frontend/`.
Не нужен для вопросов и чтения/анализа кода. Правки только в `.ai-docs/`, `.ai-tasks/`, `CLAUDE.md` — без папки задачи, но тоже не напрямую в `main`.

## 0. Термины

- **Задача** — один законченный, проверяемый кусок работы (фича, баг, рефакторинг). Если запрос пользователя состоит из нескольких независимых частей — предложить разбить на несколько задач.
- **ID задачи** — четырёхзначный порядковый номер: следующий после максимального в журнале `.ai-tasks/tasks.md`.
- **Ветка** — `<тип>/<ID>-<slug>`, где
  - тип: `feature` (новая функциональность), `fix` (баг), `refactor` (без изменения поведения), `chore` (инфраструктура, зависимости, тесты, CI);
  - slug: 2–5 слов латиницей в kebab-case, по смыслу задачи.
  - Пример: `feature/0003-payment-export-csv`.
- **Папка задачи** — `.ai-tasks/<ветка>/`, путь совпадает с именем ветки (например `.ai-tasks/feature/0003-payment-export-csv/`).
- **Репозиторий** один — корень `root.FinCtrl` (база — `main`), внутри backend `FinCtrl/` и frontend `FinCtrl.Frontend/`. Задача, затрагивающая обе части, — одна ветка и один PR.

## 1. Старт задачи

1. Проверить, что рабочее дерево чистое (`git status`). Если есть чужие незакоммиченные изменения — остановиться и спросить пользователя, ничего не стирать.
2. Обновить базовую ветку (`git fetch`, `git checkout <база>`, `git pull --ff-only`, если есть remote) и создать от неё ветку задачи. Исключение — пакетный запуск (раздел 8): там ветка создаётся от ветки предыдущей задачи пакета.
3. Если задача уже заведена в журнале со статусом `запланирована`, ветка и папка у неё уже определены. Взять существующие `about.md`/`plan.md` и сверить их с текущим кодом: номера строк и состояние файлов могли измениться. При необходимости обновить и перейти к п. 4. Если задачи в журнале нет, создать папку задачи по шаблонам из `.ai-tasks/_templates/`:
   - `about.md` — постановка: контекст, что нужно сделать, что **не** входит в задачу, критерии приемки (проверяемые пункты-чекбоксы), затронутые части (backend/frontend).
   - `plan.md` — план: шаги-чекбоксы, затрагиваемые файлы/слои (миграция → Domain → Infrastructure → Application → ApiController → Vue), какие тесты будут написаны, риски, журнал решений.
4. Добавить строку в журнал `.ai-tasks/tasks.md` со статусом `в работе` (для запланированной задачи — сменить её статус на `в работе`).
5. Если постановка неоднозначна или критерии приемки додуманы самостоятельно — показать пользователю `about.md` и согласовать критерии **до** написания кода. Для небольших очевидных задач — достаточно кратко перечислить критерии в ответе и продолжать.

## 2. Реализация

- Работать только в ветке задачи; никогда не коммитить напрямую в `main`.
- Следовать `CLAUDE.md`, `.ai-docs/workflow/styleguide.md` (UI), `.ai-docs/workflow/backend-guide.md` (backend) и граблям из `.ai-docs/project/project-summary.md`.
- Коммитить небольшими логическими шагами; сообщения коммитов — по-русски, в повелительном/описательном стиле, первая строка ≤ 72 символов (вместе с префиксом), без мусора вроде «fix», «changes».
- Первая строка сообщения коммита **всегда** начинается с номера задачи в формате `[<ID>] `, как в заголовке PR. Пример: `[0007] Исправить заголовки периодов на главной`. Это относится ко всем коммитам ветки задачи, включая правки `plan.md` и журнала (`[0007] Отметить задачу на ревью`).
- По мере выполнения отмечать шаги в `plan.md`. Если план меняется — обновить `plan.md` и записать причину в «Журнал решений».
- Не расширять объём задачи молча: найденные попутно проблемы — записать в `plan.md` раздел «Вне объёма» и сообщить пользователю (предложить отдельную задачу).
- Миграции БД — новым файлом `db/migrations/000N_*.sql`, накатить на dev-базу и проверить. Миграция должна быть идемпотентной (`IF NOT EXISTS` / `IF COL_LENGTH(...) IS NULL`).
- Не коммитить секреты, строки подключения к не-dev окружениям, отладочный код (`console.log`, закомментированные блоки), сгенерированные артефакты (`bin/`, `obj/`, `dist/`, `node_modules/`).

## 3. Тесты

### Инфраструктура
Если в репозитории ещё нет тестов — первая задача, которая его меняет, создаёт тестовую инфраструктуру (или выносит её в отдельную `chore/`-задачу, согласовав с пользователем):
- **Backend**: xUnit-проект `FinCtrl/tests/FinCtrl.Application.Tests/` (+ при необходимости `FinCtrl.Website.Tests/`), добавленный в `FinCtrl.Backend.sln`; моки — NSubstitute или Moq. Запуск: `dotnet test FinCtrl.Backend.sln`.
- **Frontend**: Vitest + `@vue/test-utils` + `jsdom`, скрипт `"test": "vitest run"` в `package.json`; тесты рядом с кодом (`*.spec.js`) или в `src/__tests__/`. Запуск: `npm run test`.

Команды выше — для человека. Агент Claude Code запускает сборку и тесты только через `node .claude/scripts/check.mjs backend|frontend|all` (`--no-tests`, `--filter <выражение>`): короткий итог, полный лог — в `.ai-tmp/`. Прямые `dotnet build/test`, `npm run build/test` и `vitest` блокирует хук `guard-raw-builds.mjs`. Распределение работы между агентами — скил `do-task` (`.claude/skills/do-task/SKILL.md`).

### Что покрывать юнит-тестами
- Новая/изменённая бизнес-логика в `FinCtrl.Application` (сервисы) — обязательно, с мокнутыми репозиториями: основной сценарий, граничные случаи, ошибки/валидация.
- Нетривиальная логика контроллеров (маппинг DTO, построение дерева, семантика null в `EditPaymentRequest`).
- Парсинг импорта (`XlsxFileFormat`/`CsvFileFormat`, поиск дублей) — на небольших фикстурах в тестовом проекте.
- Frontend: чистая логика (форматирование, агрегации, расчёт цветов тепловой карты и т.п.) — выносить в функции/composables и тестировать; компоненты — тестировать ключевое поведение, не верстку.
- Исправление бага — сначала тест, воспроизводящий баг (красный), затем фикс (зелёный).
- SQL репозиториев юнит-тестами не покрывается; проверяется вручную на dev-базе (описать проверку в `plan.md`).

Тесты должны быть детерминированными: без реальной БД, сети, текущей даты/времени (передавать дату параметром или через абстракцию).

## 4. Проверка перед PR (Definition of Done)

Все пункты обязательны; при провале — исправить и пройти чек-лист заново.

Механическая часть проверяется автоматически хуком Claude Code `.claude/hooks/pre-pr-check.mjs` (`PreToolUse`, регистрация в `.claude/settings.json`): он запускается на `git push` / `gh pr create` и при провале блокирует команду с отчётом. Ниже: **[хук]** — проверяет хук, **[вручную]** — проверка остаётся на исполнителе. Ручные пункты выполняются **до** push.

1. **Сборка** без ошибок в каждой затронутой части — **[хук]**, только для частей, затронутых диффом `main...HEAD`:
   - backend: `dotnet build FinCtrl.Backend.sln` — 0 ошибок; нет предупреждений в изменённых файлах (хук смотрит все предупреждения в файлах диффа, не только новые);
   - frontend: `npm run build` — без ошибок.
2. **Все тесты зелёные**: `dotnet test FinCtrl.Backend.sln` и/или `npm run test` — **[хук]** (если тестовый проект/скрипт `test` уже есть). Тесты не удалять/не отключать ради зелёного прогона — **[хук]** ловит удалённые тестовые файлы и `Skip =`/`.skip(`/`.only(`; остальное — **[вручную]**.
3. **Ручная проверка**: для UI/API-изменений — запустить preview (`backend`, `frontend` из `.claude/launch.json`) и пройти сценарии из критериев приемки; нет ошибок в консоли браузера и логах backend — **[вручную]**.
   - **Скриншоты запрещены** (`computer` с `screenshot`/`zoom`, `browser_batch` со скриншотом) — они дорогие по токенам. Проверять текстовыми инструментами: структуру и тексты — `read_page`/`get_page_text`/`find`, взаимодействие — `computer` (click/type) или `form_input` с последующим `read_page`, цвета/размеры/отступы — `javascript_tool` (`getComputedStyle`, `getBoundingClientRect`), ошибки — `read_console_messages`/`preview_logs`, API — `read_network_requests`. Пруф проверки в PR — текстом (что проверено и какие значения получены), не картинкой.
4. **Критерии приемки** из `about.md` выполнены — **[вручную]**; все отмечены (нет `- [ ]`) — **[хук]**.
5. **Самопроверка диффа** (`git diff <база>...HEAD`): **[хук]** — нет `console.log`/`debugger`/`Debugger.Break`, сгенерированных артефактов (`bin/`, `obj/`, `dist/`, `node_modules/`), `.env`/`appsettings.Production*`, паролей в строках подключения; **[вручную]** — нет лишних файлов, изменения соответствуют задаче.
6. **Документация**: при существенных изменениях обновлён `.ai-docs/project/project-summary.md` (API, грабли, история доработок) — **[вручную]**; хук лишь напоминает, если код менялся, а документ нет.

Дополнительно хук проверяет предусловия: ветка не `main`, имя по шаблону `<тип>/<ID>-<slug>`, рабочее дерево чистое, есть строка задачи в журнале и `plan.md`, нет `--force`/`--no-verify`. Ветки, меняющие только `.ai-docs/`, `.ai-tasks/`, `CLAUDE.md`, проверяются без папки задачи и сборок.

Если хук заблокировал команду — исправить причину, закоммитить и повторить; не обходить (переформулировкой команды, правкой/отключением хука). Успешная проверка кэшируется по SHA `HEAD` (`.git/finctrl-dod-ok`), поэтому `gh pr create` после push не пересобирает проект. Ложное срабатывание — сообщить пользователю и исправить хук отдельной задачей.

## 5. Pull Request

Только после того, как пункт 4 полностью пройден:

1. Запушить ветку: `git push -u origin <ветка>`.
2. Создать PR в базовую ветку через `gh pr create`:
   - заголовок: `[<ID>] <краткое описание>`;
   - тело: цель (из `about.md`), что сделано, критерии приемки (чекбоксы), как проверено (команды сборки/тестов и их результат, ручные сценарии), миграции БД, если есть;
3. Не мёржить PR самостоятельно и не включать auto-merge — мёрж делает пользователь.
4. Если `gh` недоступен, не авторизован или у репозитория нет `origin` — не обходить правило: сообщить пользователю, что именно мешает, и что ветка готова (по возможности запушить и дать ссылку на страницу создания PR).

Запрещено: `push --force` в общие ветки, `--no-verify`, переписывание истории `main`.

## 6. Завершение

- После создания PR — статус в журнале `на ревью`, в колонку PR — ссылка.
- После мёржа (сообщает пользователь) — статус `выполнена`; локальную ветку можно удалить.
- В `plan.md` дописать итог: что сделано, что осталось/отложено.
- Если задача остановлена — статус `отложена` (с причиной в `plan.md`) или `отменена`.

## 7. Журнал задач

`.ai-tasks/tasks.md` — единая таблица по всем задачам, новые строки добавляются вниз.
Статусы: `запланирована` → `в работе` → `на ревью` → `выполнена`; а также `отложена`, `отменена`.
`запланирована` — задача заведена в бэклог: ID, ветка и папка с `about.md`/`plan.md` определены, но работа не начата и ветка не создана. Бэклог заводится docs-only PR'ом (только `.ai-tasks/`, `.ai-docs/`). Порядок и зависимости задач фиксируются в документе-источнике, например `.ai-docs/project/architecture-audit.md`.
Одновременно `в работе` должна быть, как правило, одна задача; при переключении на другую — текущую перевести в `отложена`.
При возобновлении работы в новой сессии — сначала прочитать журнал и `plan.md` активной задачи.

## 8. Пакетный запуск задач

Несколько запланированных задач можно выполнить автономно подряд, без мёржа между ними. Готовый промт для запуска — `.ai-docs/workflow/batch-run-prompt.md`.

- **Оркестратор** — сессия, в которую пользователь вставляет промт. Сам код не пишет: по очереди запускает для каждой задачи отдельную сессию (`start_session`, `context: "fresh"`, `use_worktree: false`), ждёт её завершения, проверяет результат и запускает следующую. Свежая сессия на задачу заменяет `/clear`: контекст предыдущих задач не тянется и не оплачивается повторно.
- **Модель и effort** задаются оркестратором на каждую задачу (таблица в промте). Сессия может получить модель не выше модели оркестратора, поэтому оркестратор запускается на старшей модели; его собственные ходы короткие.
- **Стек веток**: ветка задачи N создаётся от ветки задачи N−1 (первая — от `main`), PR задачи N открывается в ветку задачи N−1 (`gh pr create --base <ветка N−1>`), первый — в `main`. Хук сравнивает с `main`, поэтому его проверки (сборка, тесты, папка текущей задачи) проходят и в стеке. Мёржить PR по порядку, начиная с первого, с удалением ветки — GitHub сам перенацелит следующий PR на `main`.
- **Остановка**: если задача не дошла до PR (хук не пропускает, критерии не выполнить, нужна информация от пользователя) — пакет останавливается, оркестратор сообщает, на какой задаче и почему. Следующие задачи не запускаются: они строятся на её ветке.
- Задача сессии-исполнителя заканчивается созданием PR и записью `на ревью` в журнале; статус `выполнена` ставится после мёржа, как обычно.
