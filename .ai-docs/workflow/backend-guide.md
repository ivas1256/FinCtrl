# FinCtrl — Backend: код-стайл и архитектура

Правила для кода в `FinCtrl/` (только проекты из `FinCtrl.Backend.sln`). Основа — SOLID, Clean Architecture и DDD, но **в облегчённом виде**: проект небольшой, личный, поэтому архитектура не должна раздувать код. Если правило из книги добавляет слой, интерфейс или класс, который ничего не даёт сейчас, — не добавлять.

**Как применять:**
- Новый код пишется по этому гайду.
- Существующий код не переписывается «заодно». Файл, который правится в задаче, можно подтянуть к гайду в пределах задачи (using-и, nullable, мелкий рефакторинг). Крупные переделки (перенос интерфейсов, разбиение контроллера) — отдельной `refactor/`-задачей.
- Если правило мешает и делает код хуже — отступить от него и записать причину в «Журнал решений» `plan.md`.

## 1. Принципы (коротко)

| Принцип | Что значит у нас | Чего **не** делаем |
|---|---|---|
| **SRP** | Контроллер — HTTP, сервис — сценарий/бизнес-правила, репозиторий — SQL. Класс > ~300 строк или метод > ~50 строк — повод разделить. | Не плодим классы по одному методу. |
| **OCP** | Расширяемые варианты (форматы импорта, группировки) — через интерфейс + реализации (как `IFileFormat`). | Не делаем точки расширения «на будущее». |
| **LSP / ISP** | Интерфейсы узкие, под нужды потребителя. | Нет generic `IRepository<T>` на всё. |
| **DIP** | Application зависит от абстракций репозиториев, Infrastructure их реализует. | Интерфейс заводим только там, где есть граница слоя или нужен мок в тесте. Domain-сущности, DTO, хелперы — без интерфейсов. |
| **Clean Architecture** | Зависимости направлены внутрь: `Website → Application → Domain`, `Infrastructure → Application, Domain`. | Нет отдельных проектов под Use Cases/Ports/Adapters, нет MediatR/CQRS. |
| **DDD** | Бизнес-правила и инварианты — в сущностях и сервисах Application; единый язык (Payment, PaymentSource, Account, Category, Tag). | Нет aggregate/event-ceremony, доменных событий, спецификаций. Value object — только когда реально убирает дублирование или ошибки. |
| **KISS / YAGNI** | Самое простое решение, которое корректно и тестируемо. | Нет AutoMapper, FluentValidation, Result-библиотек без явной необходимости. |

## 2. Структура решения, слои и зависимости

```
FinCtrl/
├── FinCtrl.Website/                      — ApiController'ы, DTO запросов/ответов, маппинг, DI-композиция (Startup)
├── src/
│   ├── main/                             — основной код приложения
│   │   ├── FinCtrl.Domain/               — сущности, value objects, enum'ы, доменные правила
│   │   ├── FinCtrl.Application/          — сервисы (сценарии), интерфейсы репозиториев, исключения приложения
│   │   └── FinCtrl.Infrastructure/       — реализации репозиториев (Dapper + SQL), подключение к БД, парсинг файлов
│   └── common/                           — переиспользуемый код, не привязанный к предметной области
│       ├── FinCtrl.Common/               — общее для всех слоёв (DateRange, хелперы)
│       ├── FinCtrl.Common.Domain/        — общее для Domain (базовые типы сущностей/value objects)
│       ├── FinCtrl.Common.Application/   — общее для Application (базовые исключения, абстракции)
│       └── FinCtrl.Common.Infrastructure/ — общее для Infrastructure (RepositoryBase, IDbConnectionFactory)
└── tests/                                — юнит-тесты, по проекту на тестируемый проект
    ├── FinCtrl.Application.Tests/
    └── ...                               — FinCtrl.<Проект>.Tests
```

- `src/main` — код FinCtrl; `src/common` — код, который можно перенести в другой проект без изменений. В `common` нет ничего про платежи, категории и т.п.
- `src/common` делится по тем же слоям: `FinCtrl.Common.<Слой>` нужен только этому слою и подключается только им (и вышележащими); `FinCtrl.Common` — общий для всех. Проект `Common.<Слой>` заводится, когда в нём появляется первый код (сейчас есть `FinCtrl.Common` и `FinCtrl.Common.Infrastructure`).
- `tests/` — см. раздел 8.

### Кричащая архитектура (Screaming Architecture)

Структура папок должна «кричать» о предметной области, а не о технических слоях: открыв проект, видно `Payments/`, `Categories/`, `Tags/`, `Accounts/`, а не `Services/`, `Repositories/`, `Helpers/`.
- Внутри каждого слоя код группируется **по фичам**: `Application/Tags/`, `Infrastructure/Tags/`, `Controllers/TagsApi/`. Всё, что относится к фиче в этом слое (сервис, интерфейсы, исключения, вспомогательные типы), лежит в её папке.
- Технические папки (`Services/`, `Models/`, `Helpers/`, `Utils/`) верхнего уровня не заводить. Код, общий для нескольких фич, — в папку по смыслу (`Statistic/`, `Import/`) или в `src/common`, если он не про домен.
- Namespace повторяет путь папки: `FinCtrl.Application.Tags`.

### Зависимости

Правила:
- Application **не** ссылается на Infrastructure (с задачи 0014). Интерфейсы репозиториев и других внешних зависимостей (например `IFileFormat`/`IFileFormatFactory` импорта) — в Application (`Application/<Фича>/I<Entity>Repository.cs`), реализации — в Infrastructure (`internal`), регистрация — в `AddInfrastructure()`. Парсинг файлов (EPPlus, `TextFieldParser`) — в Infrastructure.
- Website ссылается на Infrastructure **только** ради `AddInfrastructure()` в `Startup`. Контроллеры работают только с сервисами Application, не с репозиториями.
- Read-модели для отчётов/дашборда (`DashboardSummary`, `MainStatistic*`) — допустимы в Domain или Application; это не сущности, им не нужно поведение.

## 3. Domain

- Сущность — `class` с идентификатором `int <Entity>Id`. Не использовать `record` для мутабельных сущностей (value-equality + изменяемые списки = сюрпризы); `record` — для неизменяемых value objects и DTO.
- **Поведение рядом с данными**: правило, которое касается одной сущности, — метод/свойство сущности (`Payment.CalculatedCategory`, `Category.IsIncludeInTotalResults()`), а не `if` в контроллере. Логику, уже живущую в сущности, не дублировать в других слоях.
- Создание — через конструктор или статическую фабрику (`CreateNew`, `FromExcelPayment`), которые гарантируют валидное состояние. Публичные сеттеры допустимы (нужны Dapper'у и правке), полной инкапсуляции не добиваемся.
- Обязательные строки — инициализировать (`= string.Empty`) или делать `required`; необязательные — `string?`. Nullable-предупреждений в новом коде быть не должно.
- **Без магических значений**: id категорий, служебные значения, строки из банковского файла — именованные константы или enum (`CategoryIds.Savings`, а не `33`).
- Деньги — `decimal`; знак суммы: расход `< 0`. Отдельный `Money` не вводим, пока нет мультивалютности.
- Даты: `DateRange.To` — исключающая граница. Текущее время не брать через `DateTime.Now` в логике — передавать параметром или через `TimeProvider` (иначе не протестировать).
- Domain не знает о БД, HTTP, DTO, Dapper.

## 4. Application

- Сервис = `I<Feature>Service` (public) + `<Feature>Service` (internal), регистрация `AddScoped` в `AddApplication()`.
- **Интерфейс и реализация в одном файле**, если они в одном слое и в интерфейсе меньше 10 методов: сначала интерфейс, затем класс; файл называется по реализации (`TagService.cs`). Интерфейс на 10+ методов — в отдельном файле `I<Name>.cs`. Интерфейс и реализация из разных слоёв (репозиторий: интерфейс в Application, реализация в Infrastructure) — всегда в разных файлах. Существующие пары файлов не сливать без причины.
- Сервис отвечает за **сценарий**: валидацию входных данных, бизнес-проверки (уникальность имени, существование связанных сущностей), оркестрацию репозиториев, транзакционную границу.
- Простой CRUD может быть тонким сервисом — это нормально, но проверки вида «имя уже существует» живут здесь, а не в контроллере.
- Сервис может звать другой сервис, если это переиспользование сценария; избегать циклов и цепочек > 2.
- **Ошибки** — исключения приложения, а не `null`/строки/`NotImplementedException`:
  - `NotFoundException` — сущность не найдена (→ 404);
  - `ValidationException` / `DomainException` — некорректные данные или нарушение правила (→ 400);
  - заводятся в Application первой задачей, которой они понадобятся, вместе с глобальным обработчиком в Website (ProblemDetails).
  - `NotImplementedException` — только для реально не реализованного кода, не как бизнес-ошибка.
- Возвращать доменные сущности или read-модели; `IReadOnlyList<T>`/`List<T>` вместо ленивых `IEnumerable<T>`. Для пагинации — именованный тип или кортеж `(Items, TotalCount)`.
- Логирование — `ILogger<T>` в сервисах для значимых событий (импорт: сколько создано/пропущено; неожиданные ситуации). Не логировать и тут же пробрасывать одно и то же исключение на каждом слое.

## 5. Infrastructure (Dapper + SQL)

- Репозиторий наследует `RepositoryBase`, реализация `internal`, регистрация `AddScoped` в `AddInfrastructure()`.
- Методы репозитория — про данные (`GetById`, `GetByName`, `GetListPaged`, `Create`, `Update`, `Delete`, `Exists`), без бизнес-правил.
- **Только async Dapper** (`QueryAsync`, `ExecuteAsync`, `ExecuteScalarAsync`). Никаких синхронных вызовов в async-методах, `.Result`, `.Wait()`.
- **SQL**:
  - verbatim-строки `@"..."`; общий список колонок/SELECT сущности — один `private const string` на репозиторий, переиспользуется во всех запросах (не копипастить колонки);
  - только параметры (`@Name`), никакой конкатенации пользовательских значений; динамический `ORDER BY` — только через whitelist (`switch`);
  - фильтрация, сортировка, пагинация — **в SQL**, не в памяти;
  - Id после вставки — `OUTPUT INSERTED.<Id>` + `ExecuteScalarAsync<int>`;
  - soft delete (`IsDeleted`) учитывать во всех выборках, где он есть;
  - избегать N+1: связанные данные — одним запросом / `WHERE Id IN @Ids`, деревья — одним запросом и сборкой в памяти.
- Многошаговые записи (DELETE+INSERT связей, удаление с зависимостями, массовый импорт) — **в транзакции**:
  - внутри одного репозитория — `await using var tx = await BeginTransaction();` … `await tx.Commit();` (хелпер `RepositoryBase`);
  - сценарий из нескольких репозиториев/сервисов — в сервисе Application через `IUnitOfWork.BeginTransaction()` (`FinCtrl.Common`);
  - освобождение без `Commit` — откат; вложенный `BeginTransaction` входит во внешнюю транзакцию, фиксирует внешняя;
  - запросы — только через хелперы `RepositoryBase` (они передают текущую транзакцию), соединение напрямую не брать.
- Маппинг: плоский internal-класс строки (`PaymentDto` с алиасами `Prefix_Column` + `MapToX()`) для сложных JOIN'ов; для простых таблиц — `QueryAsync<T>` с совпадающими именами колонок. `dynamic` в новом коде не использовать.
- Новое поле таблицы — проверить **все** SELECT'ы сущности (см. грабли в `CLAUDE.md` про SELECT `PaymentRepository` и маппинги платежа).
- Миграции — см. `CLAUDE.md` и `task-workflow.md` (новый файл, идемпотентно).

## 6. Website (API)

- Контроллер: `[Route("api/[controller]")] [ApiController]`, наследует `ControllerBase`, имя `<Feature>ApiController`, папка `Controllers/<Feature>Api/`. Существующие URL не переименовывать — от них зависит фронтенд.
- Контроллер **тонкий**: принять DTO → вызвать сервис → смапить результат в DTO. Без агрегаций, построения деревьев, расчёта периодов, процентов, дефолтных диапазонов дат — это Application. Без состояния в полях контроллера.
- Наружу — **только DTO**, не доменные сущности. DTO лежат рядом с контроллером (`Controllers/<Feature>Api/`), один публичный тип на файл (маленькие вложенные record'ы одного ответа — можно вместе). Имена: `<Entity>Dto`, `Create<Entity>Request`, `<Something>Response`.
- Маппинг — вручную: статические `FromModel`/`ToModel` в DTO или методы-расширения. Один маппинг на пару типов, не дублировать в разных action'ах.
- Тело запроса — явно `[FromBody]`; id в PUT — из роута (существующий `EditPayment` с id в теле — legacy, не повторять).
- Ответы: `200 Ok(dto)` — чтение/правка с результатом, `201`/`200` — создание с телом, `204 NoContent()` — без тела, `400` — ошибка валидации, `404` — не найдено. Ошибки — в формате ProblemDetails через глобальный обработчик, а не `BadRequest("строка")`.
- Под-маршруты новых action'ов — kebab-case (`bulk-tags`, `by-source/{id}`).
- Базовая проверка формы входа (обязательные поля, диапазоны) — атрибутами DataAnnotations на DTO; бизнес-проверки — в сервисе.
- В JSON-API — нормальные типы (`bool`), не HTML-формовые `"on"`.

## 7. Код-стайл C#

- Nullable и ImplicitUsings включены; новый код — без предупреждений. Лишние `using` (`System.Linq`, `System.Threading.Tasks` и т.п.) не писать.
- Новые файлы — file-scoped namespace (`namespace FinCtrl.Application.Tags;`). Существующие не переформатировать целиком без причины.
- DI — через конструктор; в новых классах допустим primary constructor. Поля — `private readonly` `_camelCase`.
- Именование: типы/методы/свойства — PascalCase, параметры/локальные — camelCase, константы — PascalCase. Суффикс `Async` **не используем** (весь I/O-код и так async — так принято в проекте). Лямбда-параметр `_` — только для игнорируемого значения.
- `var` — когда тип очевиден из правой части.
- Async до конца: `async Task` в I/O-цепочке, без `async void`. `CancellationToken` — по желанию, для долгих операций (импорт).
- Методы короткие и читаемые: ранний `return` вместо глубокой вложенности, LINQ — где он понятнее цикла.
- **XML-doc (`/// <summary>`) обязателен для всех публичных методов** (включая методы интерфейсов и action'ы контроллеров — они попадают в Swagger). Коротко, на русском: что делает метод; `<param>`/`<returns>`/`<exception>` — когда это неочевидно из имён (семантика null, исключающая граница дат, бросаемые исключения). Реализация метода интерфейса не дублирует текст — документируется интерфейс (при желании `/// <inheritdoc />`).
- Прочие комментарии — на русском, объясняют **почему**, а не что. Комментарий, расходящийся с кодом, хуже отсутствия.
- Не коммитить: закомментированный код, неиспользуемые классы/переменные/using, отладочные `Main`/`Console.WriteLine`, пустые `catch { throw; }`, `TODO` без пояснения.
- Исключения не глотать; ловить только те, что умеем обработать.
- Конфигурация — `appsettings.*.json`; для групп настроек — Options-паттерн. Секреты и не-dev строки подключения в репозиторий не коммитить.

## 8. Тесты

Требования к покрытию — в `task-workflow.md`, раздел 3.

- Тесты лежат в `FinCtrl/tests/`, отдельный xUnit-проект на каждый тестируемый проект: `FinCtrl.<Проект>.Tests` (`FinCtrl.Application.Tests` тестирует `FinCtrl.Application`, `FinCtrl.Infrastructure.Tests` — `FinCtrl.Infrastructure`: парсеры импорта и прочая логика без БД). Все тестовые проекты входят в `FinCtrl.Backend.sln`.
- **Namespace и путь теста повторяют тестируемый класс** с вставкой `.Tests` после имени проекта: `FinCtrl.Application.Tags.TagService` → `tests/FinCtrl.Application.Tests/Tags/TagServiceTests.cs`, namespace `FinCtrl.Application.Tests.Tags`.
- Один тестовый класс `<Класс>Tests` на тестируемый класс; имя теста — `<Метод>_<Условие>_<ОжидаемыйРезультат>`; структура Arrange / Act / Assert.
- Для доступа к `internal`-реализациям — `InternalsVisibleTo` на тестовый проект.

Архитектурно это означает: бизнес-логика должна быть в Application/Domain и зависеть от интерфейсов и параметров (дата, время), чтобы её можно было покрыть юнит-тестами с моками репозиториев.

## 9. Чек-лист новой фичи

1. Миграция `db/migrations/000N_*.sql` (идемпотентная).
2. Domain: сущность с правилами, без магических чисел.
3. Application: `I<Entity>Repository` (интерфейс), `I<Feature>Service` + реализация (в одном файле, если < 10 методов), валидация и бизнес-проверки, DI.
4. Infrastructure: репозиторий (async, один SELECT, параметры, транзакции где нужно), DI.
5. Website: тонкий `<Feature>ApiController` + DTO + маппинг.
6. XML-doc на всех публичных методах.
7. Юнит-тесты сервиса в `tests/FinCtrl.Application.Tests/<Фича>/`.

## 10. Известный техдолг (не повторять в новом коде)

Зафиксировано анализом кода; исправляется отдельными задачами:
- `PaymentsApiController` содержит бизнес-логику (`BuildTree`, `ToPeriodKey`, эффективная категория, фейковые категории) и состояние в полях; `DashboardApiController` — расчёт процентов и периодов.
- Проверки уникальности в `AccountsApiController`/`TagsApiController`; доменные сущности отдаются из `CategoriesApiController` и `PaymentsApiController.GetBySource`.
- `EditPayment` (правка + теги) — две записи не в одной транзакции: оркестрация в контроллере (до 0018). (Транзакции, синхронный Dapper, дублирование SELECT'ов, разные способы получить identity и N+1 дерева категорий убраны задачами 0009, 0015, 0016.)
- Пагинация/фильтрация в памяти (`PaymentRepository.GetAll`, фильтр тегов в `GetByDateRange`).
- Магические значения: категория `33`, `int.MaxValue`/`int.MaxValue - 1` для фейковых категорий, `"Списание"`/`"Пополнение"`, `"on"`, даты 1753/9999.
- `ILogger` (NLog) используется только в импорте (итог, с задачи 0016); в остальных сервисах логов нет.
- Баги: `EditPayment` падает с NRE при пустом описании/источнике.
