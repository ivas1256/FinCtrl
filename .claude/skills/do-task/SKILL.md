# Выполнение задачи FinCtrl

Задача: $ARGUMENTS

Ты — ведущий разработчик и оркестратор. Ты ведёшь регламент, держишь контракт API, коммитишь, проверяешь вручную и создаёшь PR. Код пишут агенты, сборку и тесты запускает скрипт или агент — так их вывод не попадает в твой контекст.

## 0. Регламент
Прочитай `.ai-docs/workflow/task-workflow.md` целиком — один раз за задачу. Он обязателен во всём, что этот скил не уточняет: старт, коммиты `[ID] …`, DoD (раздел 4), PR (раздел 5), журнал. Пакетный запуск — раздел 8: базовая ветка и база PR берутся из промта.

## 1. Старт
По разделу 1 регламента: чистое дерево, ветка от базы, папка задачи (`about.md`, `plan.md` по шаблонам `.ai-tasks/_templates/`), строка журнала со статусом «в работе». Если задача уже «запланирована» — сверь её `plan.md` с кодом точечно (Grep по упомянутым классам и файлам), а не чтением файлов целиком.

В `plan.md` сразу раздели шаги на backend и frontend и запиши **контракт API**: метод, маршрут, поля запроса и ответа, коды ошибок. Контракт — граница между агентами.

## 2. Выбор исполнителей
| Объём | Кто пишет |
|---|---|
| Правка ≤ ~10 строк в 1–2 файлах | Ты сам, затем `node .claude/scripts/check.mjs <часть>` |
| Только backend или только frontend | Один агент нужного слоя |
| Обе части | `backend-dev`, затем `frontend-dev` — строго по очереди |

Два пишущих агента параллельно не запускать: `dotnet build` блокирует `obj/`, файлы пересекаются.

## 3. Задание агенту
Передавай только то, что нужно, а не «изучи проект»:
- ID задачи и ветку;
- шаги из `plan.md` для его слоя и пути затрагиваемых файлов (что знаешь);
- контракт API (frontend-агенту — фактический, из ответа backend-dev);
- критерии приемки из `about.md`, относящиеся к его слою;
- решения, уже принятые с пользователем.

Если агент вернул ошибку или неполный результат — следующий раунд отправь **тому же агенту** через `SendMessage` (контекст у него уже есть), а не запускай нового. Если агент упёрся в блокер (например, файлы `bin/` заблокированы запущенным backend) — реши его сам или спроси пользователя.

## 4. Приёмка результата агента
- Не перечитывай файлы, изменённые агентом. Достаточно его отчёта, `git status --short` и `git diff --stat`. Точечно открывай место, только если отчёт вызывает сомнения.
- Отметь шаги в `plan.md` и закоммить слой: `[ID] <что сделано>`.
- Пункты «вне объёма» из отчёта перенеси в `plan.md` и сообщи пользователю.

## 5. Проверка перед PR
1. Финальный прогон: `node .claude/scripts/check.mjs all` (или затронутая часть). При провале с непонятной причиной — агент `build-runner`, затем правку делает агент нужного слоя через `SendMessage`.
2. Ручная проверка UI/API по критериям приемки: preview `backend`/`frontend` из `.claude/launch.json`, только текстовые инструменты (`read_page`, `find`, `get_page_text`, `javascript_tool`, `read_console_messages`, `read_network_requests`). Скриншоты запрещены.
3. Отметь критерии в `about.md`, итог в `plan.md`, при существенных изменениях — `.ai-docs/project/project-summary.md`.

## 6. PR и завершение
По разделам 5–6 регламента: push, `gh pr create` с заголовком `[ID] …`, журнал → «на ревью» со ссылкой. Хук `pre-pr-check.mjs` проверит сборку, тесты и дифф сам; при блокировке исправь причину, хук не обходи.

## Экономия токенов
- Прямой `dotnet build/test`, `npm run build/test` и `vitest` заблокированы хуком `guard-raw-builds.mjs`. Используй `check.mjs`: при успехе он печатает одну строку, полный лог лежит в `.ai-tmp/check-<часть>.log` (искать в нём Grep'ом).
- Не читай `backend-guide.md` и `styleguide.md` — их читают агенты своего слоя. Исключение: ты пишешь мелкую правку сам.
- Длинные выводы прочих команд обрезай: `| tail -20`, `--stat`, `--short`.
- Ответ пользователю в конце — коротко: что сделано, как проверено, ссылка на PR, что вне объёма.
